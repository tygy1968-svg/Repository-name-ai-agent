# Аудит цепочки evolution: запись и использование

Дата: 2026-10-22. Источник: server.js ветки main, прочитан через GitHub. Только исследование; продакшен не менялся.

## Подтверждено по коду

1. `sbGetImportantKuziaEvolutionForContext` (около строк 318–353) читает только записи `user_id=yulia`, `event_type IS NOT NULL`, `importance >= 4`, сортирует по убыванию timestamp, ограничивает выборку. Ошибки чтения превращаются в пустой список.
2. `formatImportantEvolutionForContext` (около строк 356–380) включает change, rule_update, axis_state и lesson, но берёт максимум 5 записей.
3. `generateReply` (около строк 2690–2840) действительно добавляет важные переходы и архивные узлы в system prompt Telegram.
4. `shouldCreateKuziaEvolutionTransition` (около строк 382–412) ищет заранее заданные подстроки пользовательского текста, включая «зафиксируй переход», «самоанализ», «непрерывность». Это не самостоятельная оценка значимости события.
5. `maybeWriteKuziaEvolutionFromTelegram` (около строк 737–781) вызывает генерацию transition, запись в БД и обновление agent_state только если сработал триггер.
6. Telegram handler (около строк 3680–3720) вызывает запись evolution ПОСЛЕ генерации и отправки ответа. Поэтому новый переход не может повлиять на ответ, который его создал; его влияние возможно на следующих обращениях.

## Ограничения, требующие проверки

- Последние пять важных переходов могут вытеснить более старое, но фундаментальное правило. Поиск по релевантности/конфликтам правил не обнаружен в этой цепочке.
- Возврат [] при ошибке чтения может маскировать отказ Supabase под «нет важных переходов».
- Сам факт включения текста правила в prompt не доказывает, что оно применяется; нужен проверяемый тест последующего ответа.
- Не проверена эквивалентность этой цепочки в голосовом agent.js и других каналах.
- Старые [ACTION]/[AGENT RESPONSE] из 8 апреля являются данными истории, а не доказательством фактического выполнения названных функций.

## Следующий инженерный шаг

Спроектировать классификатор событий с подтверждениями и механизм отбора долговременных правил по значимости, актуальности и конфликтам; провести неразрушающий тест на отдельном тестовом пользователе/окружении. Без разрешения не менять production, не писать тестовые записи в живую БД.
