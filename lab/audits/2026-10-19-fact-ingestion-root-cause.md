# Анализ причины загрязнения памяти — 19 октября 2026

Статус: анализ исходников production main без изменения production. Проверено по `server.js` blob `cfb78d67cb6ba7dd21ae6628909e0a2740460f9a`.

## Подтверждённая цепочка
1. Telegram webhook (примерно строки 3676–3686) вызывает `extractFacts(text)` **перед** формированием ответа, затем для каждого результата вызывает `sbSaveFact(userId, f)`.
2. `extractFacts` (2330–2370) просит модель извлечь «долговременные факты» и явно задаёт преобразование «Если указан бренд → Пользователь развивает бренд <Название>». Правило не различает тест, гипотезу, цитату, отрицание, ролевой сценарий и личное утверждение.
3. `sbSaveFact` (1648–1708) классифицирует факт; для категории brand сначала вызывает `sbDeleteFactsByPattern`, а затем создаёт embedding и POST в `memory` с `type: "fact"`, `weight: 1.0`. Удаление старых фактов не обёрнуто в одну транзакцию с успешным созданием новой записи.
4. Для чтения Telegram используется числовой `msg.from.id`, тогда как телефонный агент использует `KUZYA_OWNER_USER_ID="yulia"`; `kuzia_interactions` в Telegram тоже пишутся под `yulia`. Это подтверждённая разница пространств идентификаторов, но её фактические последствия нужно проверять по строкам базы.
5. Лабораторная защита только на этапе `generateReply` **не устраняет** загрязнение: к моменту ответа факт уже мог быть сохранён.

## Вывод
Подтверждён архитектурный путь, по которому вымышленный бренд мог попасть в долговременную память. Происхождение конкретных строк AMADORA PRO пока не доказано историческими логами; не приписывать их именно этому пути без сопоставления времени и источников.

## Требования к исправлению
- Разделить извлечение кандидата и утверждение факта; сохранять provenance (канал, сообщение, тип свидетельства, тест/цитата/факт).
- Не считать «модель выделила факт» достаточным подтверждением истинности.
- Для неоднозначных личных фактов — статус `candidate` и подтверждение пользователя, без автоматического включения в активную память.
- Никаких автоматических DELETE при новом кандидате; замена факта только после проверки и с журналом изменений.
- Учитывать отрицания и опровержения как отдельный тип события; хранить историю без превращения её в активный факт.
- Проверять идентификатор пользователя одинаково во всех каналах, сохраняя внешние channel IDs как связи.
- Регрессионные тесты: явное личное утверждение; тестовый вымышленный бренд; цитата; отрицание; опровержение; сбой embeddings; сбой POST после подготовки замены; перезапуск и смена канала.

## Ограничения
Никакие изменения production main, Supabase или Render не производились. Исправления следует испытывать в лабораторной ветке и на синтетических данных.
