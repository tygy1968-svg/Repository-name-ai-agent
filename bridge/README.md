# Кузя и личный дот: план пересборки и проверяемый прототип

11 ноября 2026 года. Основание: Юля разрешила пересобрать Кузю вокруг связи с личным дотом, чтобы телефон и Telegram пользовались общими задачами и контекстом.

## Цель и предел подтверждённого

Цель — дот ведёт долгие задачи и решения; Telegram и телефон Кузи дают доступ к этой работе. Для пользователя сохраняются одна история поручений, источники, понятные результаты и согласованный стиль.

Постоянная связь с реальным дотом **ещё не установлена**. Первый ручной обмен через его GitHub-подключение подтверждён (см. ниже). Эта ветка содержит очередь, HTTP MCP-транспорт и отдельный обработчик постоянных webhook-событий. В Supabase установлено изолированное хранилище моста и проверена синтетическая запись; существующие память/звонки/архивы не менялись. Публичный endpoint с реальной OAuth-авторизацией пока не включён. Production server.js/agent.js файлы моста не импортируют; модель/голос/телефон не переключены.

Официально подтверждены использование плагинов дотом и MCP Events. События обрабатываются асинхронно: HTTP 2xx означает получение, а не завершение работы. Публичный синхронный API вызова именно личного дота с гарантированной задержкой для телефонного разговора не подтверждён. Замена API-модели не означает перенос личного дота или его внутренней памяти.

## Предлагаемое разделение

| Часть | Ответственность |
| --- | --- |
| Личный дот | Разбор сложного запроса, работа инструментами в разрешённом объёме, подготовка результата и явных решений |
| Общий журнал и контекст | Поручения, даты, авторство, исходные сообщения, результаты, ссылки; отдельные статусы намерения/попытки/успеха |
| Телефонный обработчик | Распознавание, очередность реплик, перебивание, быстрое короткое произнесение ответа, проверка доступа |
| Telegram Кузи | Ввод поручений и получение готовых результатов в личном чате владельца |
| Мост | Авторизация, доставка событий, очередь, повторные попытки, квитанции, контроль актуальности результата |

Дот не получает прямой service-role ключ БД. Он использует только узкие авторизованные инструменты моста. Скрытые заметки дота не экспортируются автоматически; общими становятся явно прочитанные и сохранённые записи. Слова звонящего не превращаются в поручение Юли или проверенный факт.

## Пилот в две стороны

1. После существующей проверки владельца сервер сохраняет одно явное поручение Юли. Ключ повтора — исходный Telegram message ID либо call ID + turn ID. Ответы ассистента и чужие сообщения новых задач не создают.
2. Сервер отправляет событие `kuzya.task.created` подписанному callback активной подписки. Событие содержит только ID задачи, источник и время. Весь личный текст читается отдельным инструментом после авторизации.
3. Дот вызывает `kuzya_list_tasks` и `kuzya_claim_task`, получает временную аренду, затем при необходимости `kuzya_read_context` с отдельным scope.
4. Дот вызывает `kuzya_complete_task`: ответ, ссылки/ID источников, уникальный ID результата и токен аренды. Поздний старый исполнитель не перезаписывает нового; повтор того же результата не создаёт новую запись.
5. Кузя получает результат через собственный backend. Для Telegram отправляет в личку владельца. Для телефона ещё раз проверяет доступ, текущий звонок, текущую реплику и срок ожидания.
6. Сохранение результата и доставка разделены. Telegram message ID — квитанция отправки, а не прочтения. Аудиотранскрипт — не доказательство услышанного. При неоднозначном таймауте доставки требуется сверка, а не слепая повторная отправка.

## Почему телефон вводится отдельно

Сначала измеряется полный реальный цикл Telegram → событие → личный дот → инструмент результата → Telegram. Локальная управляемая шкала времени в тесте проверяет арифметику, а не скорость дота.

Затем в отдельных разрешённых разговорах собираются P50/P95 времени до первого звука и полного ответа, точность фактов и обработки уточнений. Пробный предел ожидания результата для одной телефонной реплики — 8 секунд; это проектное ограничение, не заявленная скорость сервиса. Если дот не укладывается, сложная задача продолжается фоном, а результат возвращается в Telegram. Голос не должен долго молчать, притворяться дотом или произносить запоздалый ответ поверх нового вопроса.

Чтобы разговор оставался содержательным, телефон получает ограниченный актуальный пакет общих решений, текущих задач и релевантных воспоминаний с версией/датой и источниками. Один лишь стиль голоса или наличие связи не гарантирует понимания. Сравниваются ответы до/после на одинаковых сценариях; автоматическое переключение всех реплик пока не вводится.

## Что реализовано в прототипе

- `task-queue.js`: атомарная очередь через внедрённый адаптер, дедупликация, ограничение ёмкости, аренды исполнителя, срок задачи, отмена, конфликтующие повторы, происхождение результата, защита телефонной реплики и раздельная квитанция доставки.
- `json-store.js`: реальное сохранение файла через temporary + fsync + rename, права 0600, последовательные транзакции одного процесса. Используется только с синтетическими данными. Это не production-БД и не решение конкуренции нескольких процессов.
- `tool-adapter.js`: пять инструментов с узкими scopes; принадлежность задачи определяется проверенной сервером identity, не аргументом модели. `enqueue`, отправка сообщений, новый звонок и выполнение покупок инструментами дота не открыты. Верификатор токена и чтение памяти внедряются извне и по умолчанию не подключены.
- `test/dot-bridge.test.js`: синтетический круг задачи, перезапуск хранилища, параллельные повторы, разные владельцы, истечение аренды, отмена, смена реплики, ошибки хранения и неоднозначная доставка.

## Первый реальный тест без браузерного входа помощника

Юля уже пользуется дотом в своём приложении ChatGPT. Поэтому для проверки его существующего GitHub-подключения вход в отдельном браузере помощника **не требуется**. Подготовлен [один синтетический обмен](pilot/README.md): дот читает request.json в этой ветке и записывает только response.json; помощник читает результат через свой GitHub-коннектор. Запуск выполняет Юля одним поручением в существующем чате дота. Успех проверяется по фактическому файлу/коммиту и ответу дота, а не по заявлению «я подключён».

Это отдельный этап проверки возможностей, без взаимодействия с Google и без обхода запрета на просмотр страницы его входа. В связанном Slack проверены каналы и участники с включёнными ботами: готовая личность дота там не обнаружена; использование Slack нельзя объявлять подключённым.

## До включения постоянного моста

1. После первого синтетического обмена проверить в аккаунте возможность добавить свой MCP-плагин и использовать события именно в личном доте. Это можно делать из уже авторизованного приложения Юли; не считать получение Google-пароля обязательным условием всей работы. Автоматическая проверка отклонила просмотр страницы Google в отдельном браузере помощника; этот путь приостановлен, запрет не обходится.
2. Выбрать существующего OAuth 2.1 провайдера с MCP discovery, resource/audience, PKCE S256 и CIMD/DCR. Не создавать самодельную авторизацию на копировании ключа БД. На каждом запросе проверять issuer, audience, подпись, срок, scopes, отзыв и привязку владельца.
3. Подключить установленный изолированный адаптер БД/outbox к серверному runtime с имеющимися серверными реквизитами. RLS включён; клиентские роли не получают чтения/записи. Подписки и попытки сохраняются; ключ шифрования должен быть стабильным секретом сервера.
4. Включить подготовленные MCP Events только вместе с реальной OAuth-проверкой и серверным обработчиком отзыва доступа. Callback challenge, DNS pinning, HTTPS, запрет private IP/redirects, Standard Webhooks и ограниченные повторы проверены локально; настоящий callback ChatGPT ещё не проходил проверку.
5. Подключить плагин, дать доту одну явную инструкцию обработки очереди; проверить синтетический полный круг, дубли, отзыв и остановку подписки. До этого `dotConnected=true` не выставляется.
6. После реального пилота подключить выбранные поручения владельца из Telegram, затем личные вопросы телефона. Обычные звонящие остаются без доступа к личному доту/памяти.

## Приёмочные сценарии

| Сценарий | Ожидаемый результат |
| --- | --- |
| Юля даёт задачу в Telegram | Ровно одна задача, результат реального дота с источниками возвращается в тот же личный канал |
| Повтор webhook/результата | Та же задача/квитанция; нового поручения и петли ответов нет |
| Дот/сервер перезапущен | Задача сохранена; протухшая аренда безопасно переходит новому исполнителю |
| Чужой звонящий просит личную историю | Личная история закрыта; доступно оставить сообщение Юле |
| Юля перебила телефонный вопрос | Старый ответ не озвучивается поверх нового; информация может остаться в истории |
| Память частична/источник недоступен | Это явно отражено в ответе, не объявляется отсутствием события |
| Таймаут доставки результата | Сохранение не путается с отправкой; при неизвестном исходе проводится сверка |
| Реальный дот отвечает медленно | Телефон не ждёт бесконечно; фоновый результат возвращается в Telegram |

## Подтверждённый обмен и следующий слой, 11 ноября 2026

Юля передала ответ своего дота со ссылкой на [коммит a6f826b](https://github.com/tygy1968-svg/Repository-name-ai-agent/commit/a6f826bb593a7ae5d1ac4f036453f5b5470bb2fc). Через GitHub независимо прочитаны сам commit и три файла на его точном SHA. В коммите добавлен только `bridge/pilot/response.json`. Ответ совпал с request ID/challenge, исправленной записью `note-2`, датой `2026-12-03` и временем `16:40`. `node bridge/pilot/verify.js` вернул `response_data_validated`. Принадлежность запуска личному доту основана на переданном Юлей ответе; подписи агента/машинной аттестации нет. PR остаётся draft и не слит. Это реальный единичный обмен через подключение, не постоянная очередь и не измерение времени ответа в звонке.

`mcp-router.js` добавляет настоящий stateless Streamable HTTP транспорт на официальных `@modelcontextprotocol/server@2.4.0` и `@modelcontextprotocol/node@2.1.2` (версии зафиксированы с lockfile). Он монтируется отдельно на корень Express-приложения и требует явных HTTPS resource/issuer URL, очереди и внешнего проверяющего OAuth-токены обработчика. Рабочий server.js его не импортирует.

- Protected Resource Metadata расположен по `/.well-known/oauth-protected-resource` + pathname ресурса; 401/403 содержит `WWW-Authenticate`. Host проверяется по настроенному публичному URL, Origin — по явному списку. Bearer допускается только в заголовке. Авторизация предшествует JSON parsing, предел тела 32 KiB.
- Каждый HTTP-запрос проверяется; непосредственно перед инструментом повторно проверяются отзыв, совпадение владельца/клиента и нужное право. У инструментов строгие схемы; клиент не задаёт owner ID. Доступ к задачам и памяти разделён. Стандартный SDK отвечает за протокол, инициализацию и dispatch.
- Реальные локальные HTTP-тесты проходят discovery, initialize, список инструментов, claim → complete → повтор результата, чужого владельца, контекст, отказ после отзыва, неверный Host/Origin/JSON, лишние поля и превышение тела. Полный набор — 118/118 на Node 22.23.4. Синтетическая авторизация в тестах не является OAuth-провайдером для установки.
- SSE replay не реализован. Webhook Events и сохранённые подписки подготовлены отдельным адаптером (см. ниже), но не включены на рабочем сервере. Публичного endpoint и `dotConnected=true` нет. Authenticate обязан проверять подпись, issuer, resource/audience, срок, отзыв и серверную привязку владельца. Успешный локальный ответ не снимает эти требования.

Read-only проверка публичного discovery текущего Supabase проекта вернула HTTP 404, `feature_disabled`, `OAuth server is disabled`. Поэтому существование базы не означает готовую авторизацию. Текущая документация Supabase подтверждает OAuth 2.1 Server и passwordless вход, но OAuth custom scopes пока не поддерживаются. Перед выбором этого провайдера нужны проверенные resource-bound claims и отдельное согласование прав приложения; нельзя объявить `openid` эквивалентом доступа к памяти или выдать обычный токен `aud=authenticated` за токен моста. Настройки Auth/таблицы/почтовые шаблоны не изменялись, код входа не отправлялся.

Следующий этап: завершить выбор и подключение OAuth-провайдера с проверенной привязкой ресурса/прав/Юли, включить подготовленный runtime с постоянным ключом шифрования, затем подключить в уже открытом приложении Юли и проверить реальный автоматический полный круг. До этого телефон не переключать на дота.

## Постоянное хранение и события

`supabase-store.js` реализует optimistic CAS транзакции через две узкие RPC-функции. Миграция `20261111191215_kuzya_dot_bridge_state.sql` установлена в текущем проекте; номер локального файла согласован с реально возвращённой migration history. Файл первоначально создан штатным CLI3.1.0 (`migration new`), SQL не меняет старые таблицы/архивы или Auth. Таблица `kuzya_bridge.state` в отдельной схеме, с RLS и доступом только service_role; public RPC — SECURITY INVOKER, search_path пустой, EXECUTE для PUBLIC/anon/authenticated отозван. Подписи и ключ БД доту не выдаются.

В одной сохранённой версии находятся задача и её metadata-событие: сбой записи не оставляет половину операции. Конфликты версий повторяют только синхронную функцию без внешних действий. Неоднозначный таймаут записи разрешается по уникальной квитанции commit_id; без подтверждения возвращается bridge_commit_unknown. Обычное чтение не меняет версию. Предел первого запуска —1000 задач,2000 outbox записей,100 подписок и32MiB JSON; автоматической очистки/архивации нет. Это ограниченное начальное хранилище, а не масштабируемая очередь без ограничений.

`events.js` сохраняет подписки, аренду доставки, попытки, сроки и квитанции в том же store. ID подписки детерминирован из подтверждённого владельца/клиента/callback/event/arguments. До активации проверяется подписанный одноразовый challenge; кэш проверки ограничен5 минутами, обновление через кэш не продлевает срок. Секрет и callback шифруются AES-256-GCM с привязкой ciphertext к ID подписки; нужен внешний постоянный32-байтовый ключ. Смена ключа сервера требует отдельной миграции, новый случайный ключ при каждом запуске недопустим.

`webhook-transport.js` использует стандартную библиотеку standardwebhooks1.1.1. При каждом подключении проверяет все DNS-адреса, отклоняет private/local/reserved IPv4/IPv6 и mapped addresses, затем подключается именно к проверенному адресу с исходными TLS hostname/SNI и проверкой сертификата. Нет pooling или redirects, только HTTPS443; общий deadline10секунд, ответ до64KiB, отправляемое событие до256KiB. Ротация подписного ключа имеет5-минутное окно двух подписей.

Получение2xx означает только webhook_receipt_only, задача не завершается. Повторы имеют тот же eventId и свежую подпись, ограничены6 попытками с backoff;410 отзывает подписку,413 останавливает доставку этого события. Перед каждым отправлением проверяются текущий доступ, срок и generation подписки. Unsubscribe идемпотентен и удаляет зашифрованные реквизиты подписки; уже начатый HTTPS-запрос может завершиться в пределах10секунд. События до начала подписки не воспроизводятся (`cursor:null`); новый подписчик должен один раз прочитать актуальную очередь, это часть будущей инструкции доту.

`runtime.js` соединяет очередь, RPC store, защищённый router и webhook worker. Импорт ничего не запускает; mount и startWorker выполняются только явно. Проверяющие OAuth/текущий отзыв доступа функции обязательны, без них runtime не создаётся. Worker не перекрывает собственные тики, ошибки не содержат реквизитов или текста задач. Подготовлен отдельный проверяющий модуль `oauth-access.js`, но реальный провайдер, адаптер ключей и серверных разрешений ещё не подключены; router и worker не включены в production.

В настоящей БД под service_role записан только namespace `pilot_20261111_db1`: synthetic-db-task и одно событие. Новое отдельное соединение прочитало ту же revision1/commit_id; stale CAS revision0 вернул committed=false. Anonymous/authenticated EXECUTE и schema USAGE проверены false; RLS=true. В production namespace main строки ещё нет. Это подтверждает SQL-атомарность и сохранение, но не полный HTTP RPC→runtime→ChatGPT круг. ## Проверка совместимости авторизации — 11 ноября, после ручного осмотра

Юля открыла OAuth Server в своём браузере телефона. Переключатель выключен; настройки не сохранялись. Её вход в Supabase Dashboard не переносится в браузер помощника и не создаёт пользователя приложения в Supabase Auth. Пустая таблица Auth Users не означает потерю существующей памяти Кузи. Продолжать одинаковые формы без клавиатуры и просить Юлю просто наблюдать не нужно.

Прямое включение Supabase OAuth Server **не завершает выбранную схему**. Текущая официальная документация OAuth 2.1 Flows поддерживает только `openid email profile phone`, явно не поддерживает custom scopes, а пример access token имеет `aud: authenticated`. Для нашего MCP нужны `kuzya.tasks` / `kuzya.memory.read` и токен именно для ресурса моста. Документированный пример не доказывает невозможность любой будущей настройки, но поддерживаемый прямой путь resource-bound выдачи для этого проекта пока не установлен. Права нельзя заменить на `openid` или вывести из email/user_metadata. Пока эти условия не выполнены, кнопку включения Юле не поручать.

`inspectOAuthMetadata` автоматически проверяет точное совпадение issuer, HTTPS endpoints, code flow, PKCE S256, оба scope, token authentication и наличие одного способа регистрации клиента. `metadataReady` означает только соответствие объявленных возможностей; `connected` всегда false до отдельной реальной проверки. Метод сам не запрашивает сеть и ничего не меняет.

`createResourceTokenVerifier` использует закреплённую библиотеку `jose`5.10.0 (та же версия уже была транзитивной зависимостью). Контракт намеренно узкий: RS256/ES256, `typ: at+jwt`, точные issuer и единственная audience ресурса, срок не более часа, iat/exp/nbf, sub/client_id/jti и нужные scope. Ключи берутся только через серверный `loadJwks`, не по URL/ключам из токена; он должен ограничивать сеть/кэш и быть привязан к выбранному issuer. Конфигурация и ключи не берутся от клиента MCP.

На каждом использовании `resolveGrant` должен читать актуальное серверное разрешение, его срок, привязку issuer/resource/sub/client/jti и разрешённого владельца/исполнителя. Положительный кэш полномочий запрещён; отказ/неопределённость чтения закрывают доступ. Права — пересечение проверенного scope и актуального разрешения. Срок токена повторно проверяется после асинхронного чтения. Email, user_metadata, имя/номер звонящего не участвуют в решении. Проверка подписи не заменяет отзыв разрешения. Для webhook worker по-прежнему требуется отдельный реальный `canDeliver` по owner/client.

Это **не готовый OAuth сервер и не настроенная авторизация**. Реальные `loadJwks`/`resolveGrant`/`canDeliver`, страница входа/согласия, подтверждённая привязка Юли, выпуск resource-bound токена, хранение/отзыв разрешений и приёмка не реализованы этим модулем. Новый проверяющий код не импортирован в production или runtime автоматически.

Следующий самостоятельный шаг: выбрать совместимый Authorization Server / OAuth broker, который действительно поддерживает resource indicators, наши scope, PKCE S256 и реальный способ регистрации ChatGPT; определить устойчивую привязку владельца и отзыв. Supabase оставить уже проверенным хранилищем. Затем подготовить страницу согласия под выбранный механизм. Не выдавать несовместимый токен за подключение и не менять рабочие JWT/Supabase Auth настройки ради обхода.
